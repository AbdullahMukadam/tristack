# TriStack — Journal

Append-only log of gotchas and learnings worth keeping (debugging discoveries, decisions that surprised us, framing for future work). Add a dated bullet when something non-obvious is learned; keep each entry short and specific. Do not link this file from `AGENTS.md` — it is a working log, not an entry point.

Format:
`- YYYY-MM-DD — <area>: <what happened / what we learned>.`

## Entries

- 2026-09-28 — **CLI / pip on Windows**: a standalone `pip` is often NOT on PATH on Windows even when Python is installed. The CLI hardcoded `pip` as the bin, so `pip install -e .` failed with `'pip' is not recognized`. Fix: new `apps/cli/src/utils/pip-command.ts` resolver (`resolvePipCommand`) prefers `pip`, then falls back to `python -m pip`; used by both `install-dependencies.ts` and `requirements.ts`. Note: `python -m pip --version` reports the launcher's Python version, so the baseline check now reads a real pip instead of a false "not found". A scaffold's `requires-python = ">=3.12"` still fails on Python 3.11 hosts (surfaced by pip itself), which is an environment mismatch, not a CLI bug.
- 2026-09-28 — **Templates / Tortoise ORM**: Tortoise 0.25+ moved to a context-scoped API. `Tortoise.init()` in a FastAPI lifespan no longer makes connections visible to request handlers (they run in separate tasks) → runtime error "No TortoiseContext is currently active." Fix: pass `_enable_global_fallback=True` to `Tortoise.init()` (same mechanism `RegisterTortoise` uses for FastAPI). Also: `fields.UUIDField(pk=True)` is deprecated in favor of `primary_key=True`.
- 2026-09-28 — **Templates / Python on Windows**: Python 3.14 on Windows ships no IANA tz database; `zoneinfo.ZoneInfo("UTC")` fails with "No time zone found with key UTC". Tortoise's `DatetimeField(auto_now_add=True)` hits exactly this. Fix: add `tzdata` as a dependency in generated projects. Cross-platform-safe on Linux/macOS too.
- 2026-09-28 — **Templates / schemas**: Pydantic v2 does not coerce a `UUID` object into a declared `id: str` field (lax mode still validates as `string_type` error). Shared schemas use `id: str`, so Tortoise (which returns `UUID`) must stringify at the repository layer: `ItemResponse(id=str(item.id), …)`. SQLModel is unaffected (its id is already a `str(uuid4())`).
- 2026-09-28 — **README generator**: procedural READMEs must be ORM/framework-aware about migrations — Tortoise/SQLModel/SQLAlchemy auto-create schemas on startup (no manual migration step), Alembic requires `revision --autogenerate` before `upgrade head`, and Django needs its own `manage.py migrate`. The run command also differs per framework: Django → `python manage.py runserver`, Litestar → `litestar run --reload`, Flask → `flask --app src.main run`, others → `uvicorn src.main:app`.
- 2026-09-28 — **Distribution / installers**: GitHub release assets on Windows are `tristack-windows-x64.exe.zip` (not `tristack-windows-x64.zip`); `install.ps1` must request the `.exe.zip` name. `install.sh` uses `${platform}.tar.gz` which matches the actual Linux/macOS asset names — no fix needed there.
- 2026-09-28 — **Web / Fumadocs code tabs**: the custom `CodeBlockTabs/*` components come from `fumadocs-ui/dist/mdx.js` (upstream default MDX components), not our source. Use stock Fumadocs `Tabs`/`Tab`; both render differently under our global.css overrides (we reverted the `#nd-notebook-layout` token/border-radius flattening so tabs keep upstream styling).
- 2026-09-28 — **Local testing**: run the built CLI from a scratch dir with a bare project name; absolute paths are rejected by project-name validation ("invalid characters"). Build `apps/cli/dist/cli.mjs` via `bun run build:cli` before testing. Root `package.json` script `"cli"` still references the stale `dist/cli.js` path.
- 2026-09-30 — **Boot verification / harness**: `execa` rejects with a non-zero `exitCode` instead of throwing only on signal death, so reading `result.exitCode` (not `result.failed`) is what makes install/prepare failures visible; before this, every case failed at install. Also: server stdout/stderr must be appended to the persisted failure log — asserting against `serverLog` inline loses it on the very failures you need it for.
- 2026-09-30 — **Templates / Alembic**: `script.py.mako` imported `sqlmodel` unconditionally, so Alembic autogenerate under the SQLAlchemy ORM died with `ModuleNotFoundError: No module named 'sqlmodel'`. Fix: guard the import with `{{#if (eq orm "sqlmodel")}}`.
- 2026-09-30 — **Templates / SQLAlchemy**: the declarative `Item` model declared `id = Column(String, primary_key=True)` with no default, so `POST /api/v1/items` failed with `NOT NULL constraint failed: items.id`. SQLModel and Tortoise both defaulted their ids. Fix: `default=lambda: str(uuid4())`.
- 2026-09-30 — **Templates / Flask**: the Flask route handlers are `async def`, but plain `flask` cannot run async views ("Install Flask with the 'async' extra"). Fix: depend on `flask[async]` (`{ extras = ["async"] }` in Poetry) in all three pyproject templates. Also added the missing `tzdata` dependency for Tortoise to `pyproject-poetry.toml.hbs` (the earlier Windows tz fix had only landed in the uv/pip variants).
- 2026-09-30 — **Templates / Litestar**: the whole framework scaffold was unbootable against Litestar 2.x, in five separate ways. (1) `litestar run` autodiscovers only `app`/`application` in `app.py`, and there was no root entrypoint — added a root `app.py` re-exporting `create_app`/`app`. (2) `Provide` is not importable from `litestar` (it lives in `litestar.di`), and using it as a parameter default is invalid (`unhashable type: 'Provide'`) — it belongs in the handler's `dependencies={...}`, and an async-generator provider needs `sync_to_thread=False`. (3) Route decorators passed `path` twice (`@get("/", path="/items")` → "got multiple values for argument 'path'"). (4) `lifespan=` expects a list of ASGI middleware, not an async context manager — use `on_startup=[...]`. (5) Exception handlers are invoked **without** `await`, so `async def` handlers return a coroutine and every request 500s with `'coroutine' object has no attribute 'to_asgi_response'`. Middleware: `PureMiddleware` never existed; `AbstractMiddleware` is deprecated since 2.15 and its custom `__init__` skipped the base `__init__` that sets `exclude_pattern` — use `ASGIMiddleware` with a `handle()` method and pass an **instance** (`middleware=[RequestLoggingMiddleware()]`), since `ASGIMiddleware.__call__(app)` _returns_ the ASGI callable.
- 2026-09-30 — **Boot verification / debugging**: patching the already-scaffolded project in a temp dir and re-running the server directly is far cheaper than a full regenerate-and-rebuild cycle per fix; the matrix run is the last mile, not the inner loop. Watch out for `uv` runs interrupted mid-sync — the venv is left without `typing_extensions` (a real Litestar dependency), which surfaces as a confusing in-package import error rather than a missing dependency.

- 2026-10-01 — **Templates / Go sqlite deps**: gorm+sqlite generated a `go.mod` that pulled `github.com/glebarez/go-sqlite v1.21.2` -> retracted `modernc.org/sqlite v1.33.0`, so every generated project failed to compile with `cannot use c.tls ... *modernc.org/libc.TLS as *modernc.org/sqlite/internal/libc.TLS`. Fix: also require `modernc.org/sqlite v1.34.1` directly in `go.mod.hbs` under gorm+sqlite, so MVS picks a compatible driver instead of the retracted one.
- 2026-10-01 — **Templates / Go migrations**: goose and golang-migrate migrations created `items(id, name, created_at)` but the gorm model also declares `UpdatedAt`, so `POST /items` returned 500 (`no such column: updated_at`) while `GET` worked. Fix: add `updated_at` to both migration templates, guarded by `{{#if (eq orm "gorm")}}` since only the gorm model has the field.
- 2026-10-01 — **Runtime profile / Go migrations**: goose needs its config in env vars, not flags — `-dir migrations up` after the binary path is parsed as a subcommand and fails. The working form is `GOOSE_DRIVER`/`GOOSE_DBSTRING`/`GOOSE_MIGRATION_DIR` env with a bare `up`. golang-migrate's `-database "$DATABASE_URL"` was also wrong: the literal string was passed through because Makefile-style `$$`/shell expansion does not apply when the CLI spawns the process directly. Fix: build a real DSN in `goPrepare`, and mirror it in `Makefile.hbs` via `?=` variables.
- 2026-10-01 — **Runtime profile / sqlc**: `sqlc generate` assumed a globally installed `sqlc` binary. Fix: pin it as `go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.27.0 generate` (v1.27.0 is the newest release whose own `go` directive is 1.22, matching generated `go.mod`; v1.29+ requires Go 1.23+). On Windows the codegen also needs `CGO_ENABLED=0`, otherwise the embedded MySQL parser fails to build with `cc1.exe: sorry, unimplemented: 64-bit mode not compiled in`.
- 2026-10-01 — **Templates / Go sqlx+none**: with no migration tool, sqlx had no `items` table at all (gorm got `AutoMigrate`, sqlx had nothing), so the server booted but every query failed. Fix: add `db.EnsureSchema(ctx)` creating the table with `CREATE TABLE IF NOT EXISTS`, called from `main.go` only when `orm == "sqlx" && migrations == "none"`.
- 2026-10-01 — **Shared slug**: the runtime profile needs the same project slug the templates use for DSNs, so `toProjectSlug` moved from `packages/template-generator/src/core/template-processor.ts` to `packages/types/src/project-slug.ts` (re-exported from the old path to avoid breaking importers). Duplicating the logic is a trap: the original uses `_` separators and falls back to `app`.
- 2026-10-01 — **Templates / Go README**: generated Go READMEs told users to copy `.env.example` to `.env`, but the file is emitted as `env.example` and Go never loads `.env` anyway (defaults are baked into `internal/config`). Fix: document the actual env vars (`PORT`, `APP_NAME`, `DATABASE_URL`) plus shell snippets for exporting `env.example`, and render migration/codegen commands with their required env prefix instead of the bare `label`.
- 2026-10-02 — **Templates / audit**: full read of all 177 templates, findings tracked in `docs/TEMPLATE-AUDIT.md`. Two lessons: (1) Handlebars eats any unescaped `{{...}}` in Go `html/template` files, and escaping only the opening tag of a line isn't enough (`\{{block ...}}...{{end}}` loses the `{{end}}`), so every Go template action needs `\{{`. (2) Fixes that land in `framework/<fw>/` don't reach the `frontend/htmx/` overlay that replaces the same files: the 2026-09-30 Litestar fixes (`on_startup`, middleware instance, `litestar.di.Provide` in `dependencies`) are missing from the HTMX Litestar `main.py`/`web.py`. When fixing a framework file, grep the HTMX overlay for its twin.
- 2026-10-02 — **Templates / verification loop**: the CLI generates from `packages/template-generator/dist`, not from source, so after editing `.hbs` files run `bun run build` in `packages/template-generator` (its `prebuild` regenerates `templates.generated.ts`; never hand-edit that file). A cheap check before the boot matrix: generate one project via `createVirtual` + `writeTree` into the gitignored `apps/cli/.smoke/`, then `uv sync` and run it, `ruff check .` and `mypy .`. To prove a new boot case is useful, run it against the `HEAD` version of the template and watch it fail first. Note: boot cases run with `addons: []`, so addon configs (mypy, ruff) are never exercised by the matrix.
- 2026-10-02 — **Templates / Python blank lines around Handlebars**: ruff wants exactly two blank lines before top-level definitions, but standalone `{{#if}}`/`{{/if}}` lines vanish from the output, so blank lines on both sides of a block add up differently per branch. The rule that works for every branch: no blank line before the opening tag, and the two blank lines inside each branch, directly above the definition (`content\n{{#if x}}\n\n\ndef f(): ...\n{{/if}}`). The same applies to the blank line between third-party and local import groups when the third-party imports are conditional.
- 2026-10-02 — **Templates / Flask + async ORMs**: Flask runs every `async def` view in a fresh event loop (asgiref), and `create_app()` runs `asyncio.run(init_db())` in yet another. A pooled async engine therefore hands one loop's asyncpg connection to another, and on Postgres every request fails (`InterfaceError: cannot rollback; the transaction is in error state`). SQLite hides it, because aiosqlite isn't loop-bound. Fix: `poolclass=NullPool` for Flask projects (a connection per request). The ceiling is connection setup per request; the upgrade path is a sync engine for Flask, or an ASGI framework. Tortoise can't follow the same route: closing its connections after init removes the global context (`No TortoiseContext is currently active`), and keeping them leaves aiosqlite's non-daemon worker thread alive, so the process never exits. Flask + Tortoise is now a rejected combination.
- 2026-10-02 — **Templates / SQLModel versions**: SQLModel 0.0.22–0.0.26 can't even define a table model under pydantic 2.13 (`PydanticUserError: Field 'id' requires a type annotation`). A Poetry caret on a `0.0.x` version (`^0.0.22`) pins that exact version while pydantic floats, so it's a time bomb; use an explicit range (`>=0.0.27,<0.1`). Also, the audit's "SQLModel datetimes are naive on Postgres" claim was wrong for current SQLModel, which maps `datetime` to `timestamptz`. Always confirm a database-specific claim against a real database (the Neon run caught both).
- 2026-10-02 — **Templates / Litestar 2.23+**: this supersedes the 2026-09-30 advice. `sync_to_thread=False` on a generator provider now only emits a warning ("has no effect on generators"), and dependencies that are only inferred are deprecated for 3.0. Mark the parameter `session: NamedDependency[AsyncSession]` (from `litestar.di`) and use `Provide(get_session)`. Also, a catch-all `Exception` handler intercepts `NotFoundException`/`ValidationException` (they resolve by MRO), so unknown routes became 500s; don't register one.
- 2026-10-02 — **Testing / scratch generation**: `apps/cli/test/setup.ts` wipes `apps/cli/.smoke` before and after every test run, so scratch scripts or projects kept there disappear, and its teardown has a 30 s limit that a few virtualenvs exceed on Windows. Opt-in tests that keep real installs (`python-quality.test.ts`) write under the OS temp directory and remove each case directory after it passes. On Windows, `timeout` kills `uv` but not its Python child, and a leftover server keeps the project folder locked (`EBUSY`), so kill processes by command line before regenerating.
- 2026-10-02 — **Templates / Poetry resolution**: Poetry refuses to resolve when the project's `python` range is wider than a dependency's. Our `python = ">=3.12"` (no upper bound) failed against litestar's `<4.0`, so every Poetry + Litestar project failed to install, while FastAPI projects happened to work. Use `>=3.12,<4.0`. Two more Poetry-only traps: a caret pin left Tortoise on 0.24, which lacks the `_enable_global_fallback` argument (uv projects silently got 1.x); and `django-stubs[compatible-mypy]` caps `mypy<2.4`, so pinning mypy separately makes the dev group unsolvable. Poetry can be exercised without installing it: `uvx poetry env use <python>` then `uvx poetry install` (set `POETRY_VIRTUALENVS_IN_PROJECT=true`).
- 2026-10-02 — **Templates / tests and databases**: `with TestClient(app)` runs the app lifespan (startup creates tables), so a health test written that way needs a live Postgres/MySQL in CI. Plain `TestClient(app).get(...)` skips the lifespan and works for both FastAPI and Litestar. Flask is different: `create_app()` runs `init_db()` at import, so a Flask project without Alembic needs its database even to import (recorded as a known limitation, PY-31).
- 2026-10-02 — **Verification without Docker**: when Docker isn't available, check a Dockerfile by running its steps directly. Run `uv sync --no-dev --no-install-project`, then the `CMD` binary from `.venv` with `PYTHONPATH=.`. For pip, `pip install .` in a fresh `uv venv --seed` (a plain `uv venv` has no pip). Confirm pinned image tags exist with an anonymous registry token (`https://ghcr.io/token?scope=repository:<org>/<image>:pull`, then a HEAD/GET on `/v2/<org>/<image>/manifests/<tag>`). The image build itself stays unverified until it actually runs.
